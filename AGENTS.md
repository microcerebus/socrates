# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

Start with `README.md`; it carries the architecture, setup and security model.
The notes below are the things that are not obvious from reading the code.

## Commands

- `pnpm check` is the gate: typecheck, lint, tests. Run it before claiming anything works.
- `pnpm build` runs five separate vite passes (`SOCRATES_TARGET=...`). They are not interchangeable and the first one empties `dist/`, so run the whole script rather than a single pass unless you know why.

## Sharp edges

- **Content scripts cannot be ES modules.** That is the only reason `vite.config.ts` is target-switched instead of one build. Do not "simplify" it into a single pass.
- **TypeScript is pinned to 6.x** because typescript-eslint refuses to run against TS 7. Bumping TypeScript without checking `pnpm lint` will break the gate.
- **Chrome 151 ignores `--load-extension`,** but CDP can still load it, so end-to-end browser runs *are* automatable. Launch Chrome with `--remote-debugging-port` and `--enable-unsafe-extension-debugging`, then send `Extensions.loadUnpacked` on the browser-level WebSocket; it returns the pinned id. `--load-extension` genuinely does nothing (a minimal control extension fails the same way), so do not go back to it.
  The side panel itself cannot be opened that way - `sidePanel.open()` rejects a CDP `userGesture`. Open `panel.html` as an **inactive tab in the LeetCode window** instead: the panel's `{active: true, currentWindow: true}` query then resolves to the LeetCode tab and it scrapes the real problem.
  **Do not `Page.bringToFront` the panel tab for anything that depends on which tab is active.** The docked side panel is not a tab, so in the real product that query always finds LeetCode; foregrounding the harness tab makes the panel itself the answer, so page capture, navigation-following and anything else keyed on the active tab silently stop working - a bug can look fixed or unfixed purely from this. Foreground it only to screenshot, and drive state-only assertions in the background (`requestAnimationFrame` is throttled there, so the paced reveal will not render, but state and effects run normally).
- **`pnpm build` deletes the native-host launcher.** The first vite pass empties `dist/`, and `dist/native-host/socrates-host` is written by `bin/install-native-host.sh`, not by the build. The host manifest points at that exact path, so every build silently breaks native messaging and the panel reports `native-host-missing` with no other symptom. Re-run `./bin/install-native-host.sh` after any build you intend to load.
- **The extension id is pinned** by the public `key` in `public/manifest.json`, but Chrome and Brave have each been seen to hand this build a *different* id (`lbhnejceegeplldfheefbalbfnhdafnb` and `aplbkajcnpggamonmlebeaenjhhnjpdp`). Both are registered by default and `bin/install-native-host.sh` merges rather than replaces `allowed_origins`, so registering one browser must never deregister the other.
- **The native host runs under the browser's minimal PATH.** `node` and `claude` are both referenced by absolute path (the launcher, and `~/.config/socrates/native-host.json`). Do not switch either to a bare command name. `claudePath` additionally goes stale when `claude install` moves the binary, which is why `resolveClaudePath` probes fallbacks and reports every path it tried.
- **`SOCRATES_HOST_CONFIG`** overrides the host config path; it exists so the host can be driven against a test config without touching `~/.config`.
- **Verified, not remembered.** The `claude` flags in `src/native-host/claude.ts` were each checked against the installed CLI, including that `--system-prompt` *replaces* the Claude Code system prompt and `--tools ""` really leaves no tools. `--input-format stream-json` does **not** prime history - it re-runs the model once per user message - which is why the transcript is flattened instead. Re-verify empirically before changing any of them.
- **The CLI streams, but not per token.** Measured on 2.1.226: ~1.7s of startup with no frames at all, then `system/init`, then thinking deltas every 25-300ms, then text in blocks of roughly 150 characters about every 500ms. So "streaming looks broken" is almost never a missing flag - `--include-partial-messages` is already there and works. It is either the silent head (which is why the host emits `claude-started`) or the block size (which is why `src/panel/typewriter.ts` paces them out). The header of `claude.ts` carries the full timeline.
- **A custom property that references another one resolves where it is *declared*, not where it is used.** `--rung-solid: var(--rung)` on `:root` computes against the `--rung` that does not exist there and inherits that nothing all the way down, so every rung-coloured control silently falls back. Anything rung-dependent in `styles.css` must read `var(--rung)` directly in the property that consumes it.

## Product invariants

- Replies must never exceed the unlocked rung. The prompt is the primary control (`src/prompt/`), the spoiler guard is the deterministic backstop, and `tests/prompt-gating.test.ts` covers both. Changes to rung content belong in `src/prompt/rungs.ts`, which the tests read directly.
- **The transport is a transport and nothing more.** `src/background/interview.ts` builds the system prompt, the message list and the guard; `src/background/providers.ts` only moves bytes. Anything that could affect rung discipline belongs in `interview.ts`, never in the transport.
- **No claude prose on the success path.** The run's own JSON frames are the contract, `claude auth status --json` is consulted only after a failure, and a failure we cannot name returns `claude-cli-failed` quoting the CLI verbatim. Text comes only from `stream_event` deltas - the whole-message `assistant` frames also carry synthesised API-error prose, and reading those prints "Not logged in" into the panel as though the interviewer said it. The one exception, the no-delta fallback in `runner.ts`, is gated on `subtype === 'success'`: `is_error: false` alone does **not** mean the `result` field holds assistant text, and every other subtype puts a CLI diagnostic there.
- **Settings changes are patches, never whole objects.** A click faster than a round trip can still race, so `src/panel/settings-writer.ts` owns the intent, applies patches synchronously, serialises writes and drops superseded replies. Building a write from React's render-scoped `settings` loses that race and silently undoes the previous change.
- **Claude Code hints share the user's Max usage windows.** That is stated in Settings and in the README. It is the one thing a user can be genuinely surprised by; do not quietly drop it.
- **There is exactly one way to read the page, and it is guarded.** `capturePage` in `App.tsx` is the only caller of `client.capture`; the raw read is anonymous inside it, so an unguarded capture is not something a new call site can accidentally write. Every read is stamped with `sessionWriter.epoch` - the navigation epoch, bumped whenever the panel adopts a different problem - and discarded at *resolution* if that epoch has passed. Resolution, not initiation: at initiation everything still looks consistent, and a late capture of the problem the user left otherwise classifies as an ordinary refresh and walks the panel back to it. The epoch counts problem changes rather than comparing slugs, so A → B → A is stale too. `ifStillCurrent` returns `{current:false}` rather than `null` because "navigated away" and "page unreadable" need opposite handling - the first abandons the turn, the second falls back to what is on screen.
- **Discarding stale reads is not enough on its own; the follower also settles.** Navigating A → B → C leaves two reads in flight, and if B's lands first the panel adopts B, which correctly invalidates C's read - and would strand the panel on B while the page shows C. So after every adoption the follower reads again, in the new epoch, until the page and the panel agree. It converges because a capture matching what was just adopted classifies as `refreshed`. The loop resolves ordering within one burst of tab events; it does not poll, so a later navigation is caught by its own event.
- **The panel follows the page, and a problem switch resets the ladder.** LeetCode is a single-page app, so the user can navigate with the panel open. A capture whose slug differs from the one on screen is not a stale read to discard - it is a navigation (`src/panel/problem-switch.ts`). Carrying panel state across it would run the next turn against a statement the user has left, persist the reply into the wrong session, and carry the *rung* over, which hands out rung-4 pseudocode on a problem where nothing was earned. So the old session is written under its own slug first, then `sessionWriter.setActive` makes writes for any other slug impossible, then everything resets to rung 0.
- **A saved session exists to protect the usage window, so it restores the rung too.** `src/background/transcript-store.ts` keys transcripts by problem slug and carries `startedAt` across resumes, because that is the session log's upsert key - drop it and one problem-sitting becomes several attempts that each report a shallower deepest rung than the truth. Every write clamps four separate bounds and prunes to `MAX_SESSIONS`; a transcript store with no ceiling would quietly become the largest thing the extension owns.
- The extension is read-only on leetcode.com: no typing, clicking, or submitting.
- All LeetCode selectors live in `src/content/scrape/selectors.ts` as fallback chains. DOM drift should be a one-file change, and when it is not, the paste fallback keeps the tool usable.
- **Thinking text must never leave the native host.** Extended thinking drafts the *answer* - in a measured rung-1 run the thinking block held a complete, word-counted draft of the reply. `parseClaudeLine` therefore maps `thinking_delta` to an empty `{ kind: 'thinking' }` heartbeat and drops its text. Anything that surfaces thinking content routes the whole reply around the ladder. `tests/streaming-ux.test.ts` asserts the parser cannot carry it.
- **Liveness is a heartbeat, not an edge.** `claude-thinking` repeats (throttled by `THINKING_PULSE_MS`) for as long as frames arrive without text, because `src/panel/turn-progress.ts` decides whether to say "still working - long think" purely from the gap since the last event. De-duplicating the pulses anywhere on the path freezes the stall detector, which is why `claude-code.ts` forwards every one.
- **Dark is the primary scheme** in `src/panel/styles.css`, light is the `prefers-color-scheme: light` override. Every colour is a token declared in one of those two blocks; a literal outside them will be wrong in one scheme. Check both after any UI change. The tokens follow Catppuccin (Mocha for dark, Latte for light, https://catppuccin.com/palette) with a consistent semantic mapping - keep new tokens on-palette.
- **Rung colour is a graphic, never body text.** Each rung owns a hue (`--rung-0` … `--rung-5`, cool to warm) selected only by a `data-rung` attribute. Latte's warm accents sit near 2.4:1 against Base, so rung colour is confined to bars, borders, dots and washes; prose and button labels stay `--text` / `--rung-ink`, and a filled control uses the hue itself in Mocha but a 16% wash of it in Latte. Adding a rung-coloured element means checking it in both schemes.
- **Fonts are bundled locally** under `public/fonts/` (JetBrains Mono, OFL-licensed) and loaded via `@font-face` in `styles.css`. The extension CSP forbids remote font loading, so there is no `@import` from a font host; adding a typeface means vendoring its woff2 files the same way.
