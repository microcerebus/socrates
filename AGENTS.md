# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

Start with `README.md`; it carries the architecture, setup and security model.
The notes below are the things that are not obvious from reading the code.

## Commands

- `pnpm check` is the gate: typecheck, lint, format check, tests. Run it before claiming anything works.
- `pnpm build` runs five separate vite passes (`SOCRATES_TARGET=...`). They are not interchangeable and the first one empties `dist/`, so run the whole script rather than a single pass unless you know why.
- Commits are gated by husky + lint-staged + commitlint (Conventional Commits); CI (`.github/workflows/ci.yml`) mirrors the same checks over the whole tree. See the README's Contributing section for what runs where.

## Sharp edges

- **Content scripts cannot be ES modules.** That is the only reason `vite.config.ts` is target-switched instead of one build. Do not "simplify" it into a single pass.
- **TypeScript is pinned to 6.x** because typescript-eslint refuses to run against TS 7. Bumping TypeScript without checking `pnpm lint` will break the gate.
- **Chrome 151 ignores `--load-extension`,** but CDP can still load it, so end-to-end browser runs _are_ automatable. Launch Chrome with `--remote-debugging-port` and `--enable-unsafe-extension-debugging`, then send `Extensions.loadUnpacked` on the browser-level WebSocket; it returns the pinned id. `--load-extension` genuinely does nothing (a minimal control extension fails the same way), so do not go back to it.
  The side panel itself cannot be opened that way - `sidePanel.open()` rejects a CDP `userGesture`. Open `panel.html` as an **inactive tab in the LeetCode window** instead: the panel's `{active: true, currentWindow: true}` query then resolves to the LeetCode tab and it scrapes the real problem.
  **Do not `Page.bringToFront` the panel tab for anything that depends on which tab is active.** The docked side panel is not a tab, so in the real product that query always finds LeetCode; foregrounding the harness tab makes the panel itself the answer, so page capture, navigation-following and anything else keyed on the active tab silently stop working - a bug can look fixed or unfixed purely from this. Foreground it only to screenshot, and drive state-only assertions in the background (`requestAnimationFrame` is throttled there, so the paced reveal will not render, but state and effects run normally).
- **`pnpm build` deletes the native-host launcher.** The first vite pass empties `dist/`, and `dist/native-host/socrates-host` is written by `bin/install-native-host.sh`, not by the build. The host manifest points at that exact path, so every build silently breaks native messaging and the panel reports `native-host-missing` with no other symptom. Re-run `./bin/install-native-host.sh` after any build you intend to load.
- **The extension id is derived, never written down.** It is a pure function of the public `key` in `public/manifest.json` (`scripts/extension-id.ts`), so it is the same in Chrome, Brave and Chromium. An earlier note here claimed the two browsers hand this build different ids and that both must therefore be registered; that was residue from before the key was pinned, and the second id belonged to no build of ours. `bin/install-native-host.sh` now states the whole `allowed_origins` list each run and removes anything it did not derive - that list is the host's only access control, so it has to be able to shrink. `tests/extension-manifest.test.ts` pins both the derivation and the convergence.
- **The native host runs under the browser's minimal PATH.** `node` and `claude` are both referenced by absolute path (the launcher, and `~/.config/socrates/native-host.json`). Do not switch either to a bare command name. `claudePath` additionally goes stale when `claude install` moves the binary, which is why `resolveClaudePath` treats the recorded path as a hint rather than a promise and probes fallbacks when it is dead, reporting every path it tried only if none of them hit either. Because there is no other provider left to fall back to, `bin/install-native-host.sh` always rewrites `claudePath` to whatever it just resolved, even on a rerun over an existing config - a rerun whose whole point is picking up a relocated binary must not leave the stale path behind.
- **`SOCRATES_HOST_CONFIG`** overrides the host config path; it exists so the host can be driven against a test config without touching `~/.config`.
- **Verified, not remembered.** The `claude` flags in `src/native-host/claude.ts` were each checked against the installed CLI, including that `--system-prompt-file` _replaces_ the Claude Code system prompt exactly as `--system-prompt` does (checked on 2.1.227 - and note `--help` does not list it, so `tests/claude-cli-contract.test.ts` pins it by invoking it against a missing path instead of by grepping the help text) and that `--tools ""` really leaves no tools. `--input-format stream-json` does **not** prime history - it re-runs the model once per user message - which is why the transcript is flattened instead. Re-verify empirically before changing any of them.
- **The CLI streams, but not per token.** Measured on 2.1.226: ~1.7s of startup with no frames at all, then `system/init`, then thinking deltas every 25-300ms, then text in blocks of roughly 150 characters about every 500ms. So "streaming looks broken" is almost never a missing flag - `--include-partial-messages` is already there and works. It is either the silent head (which is why the host emits `claude-started`) or the block size (which is why `src/panel/typewriter.ts` paces them out). The header of `claude.ts` carries the full timeline.
- **LeetCode is readable without the browser, and the browser needs to be headed.** Cloudflare turns away a headless/isolated Chrome on leetcode.com, so `chrome-devtools-axi` needs `CHROME_DEVTOOLS_AXI_HEADED=1` plus a persistent `CHROME_DEVTOOLS_AXI_USER_DATA_DIR`. For facts rather than markup, skip the browser: `POST https://leetcode.com/graphql/` answers `{ languageList { id name } }` and `{ question(titleSlug:){ topicTags{name} hints codeSnippets{lang langSlug} } }` to plain curl. The English wording of the console panel (verdicts, `Input`/`Output`/`Expected`/`Stdout`) is in `window.__NEXT_DATA__.props.pageProps._nextI18Next.initialI18nStore.en.console.result` on any problem page - that is where `RESULT_LABELS` came from, and where to re-check it.
- **`data-e2e-locator` is LeetCode's own test hook and outlives its class names.** `console-result` / `submission-result` carry the verdict; `console-run-button`, `console-testcase-tag`, `console-testcase-input` mark the rest of the console. Lead every new selector chain with one where it exists, and keep Tailwind fragments last. Running or submitting needs a logged-in account, so the run-result fixtures are built from the shipped bundle's JSX rather than captured live.
- **`Emulation.setEmulatedMedia` over CDP does not re-resolve `var()` in the base cascade.** Flipping `prefers-color-scheme` on a live panel leaves base-block declarations reading the _other_ scheme's tokens - a dark button on a Latte panel - while media-block declarations update. It is an emulation artefact, not a bug in `styles.css`. Always `Page.reload` after switching the scheme before screenshotting or reading computed styles, or you will chase a colour that is correct in the product.
- **A custom property that references another one resolves where it is _declared_, not where it is used.** `--rung-solid: var(--rung)` on `:root` computes against the `--rung` that does not exist there and inherits that nothing all the way down, so every rung-coloured control silently falls back. Anything rung-dependent in `styles.css` must read `var(--rung)` directly in the property that consumes it.

## Product invariants

- Replies must never exceed the unlocked rung. The prompt is the primary control (`src/prompt/`), the spoiler guard is the deterministic backstop, and `tests/prompt-gating.test.ts` covers both. Changes to rung content belong in `src/prompt/rungs.ts`, which the tests read directly.
- **Page text is fenced, and the fence is the ladder's outer wall.** Everything scraped from LeetCode goes into the turn inside a `<<<PAGE-DATA id=…>>>` block with a per-turn random id stripped from the content (`src/prompt/untrusted.ts`), and the system prompt's rule 7 says what that means. Unfenced page text next to `# TASK` is not a formatting question: a crafted statement reads as an instruction and hands out rung-5 solutions at rung 0. A new scraped field goes inside a fence; a new instruction section stays outside one. The editor language cannot be fenced (the system prompt names it mid-sentence) so it is reduced by `languageLabel` instead. `tests/prompt-injection.test.ts` holds the line.
- **The panel offers only its own shell commands.** `hostFailureToAppError` maps a validated failure code onto a constant remedy and ignores any `command` the host sent, because `ErrorNotice` renders a remedy behind a copy-to-clipboard button in a surface the user trusts. Likewise `isHostResponse` checks the frame is a shape the union names, not that it merely has an `ok` property.
- **The transport is a transport and nothing more.** `src/background/interview.ts` builds the system prompt, the message list and the guard; `src/background/providers.ts` only moves bytes. Anything that could affect rung discipline belongs in `interview.ts`, never in the transport.
- **No claude prose on the success path.** The run's own JSON frames are the contract, `claude auth status --json` is consulted only after a failure, and a failure we cannot name returns `claude-cli-failed` quoting the CLI verbatim. Text comes only from `stream_event` deltas - the whole-message `assistant` frames also carry synthesised API-error prose, and reading those prints "Not logged in" into the panel as though the interviewer said it. The one exception, the no-delta fallback in `runner.ts`, is gated on `subtype === 'success'`: `is_error: false` alone does **not** mean the `result` field holds assistant text, and every other subtype puts a CLI diagnostic there.
- **Settings changes are patches, never whole objects.** A click faster than a round trip can still race, so `src/panel/settings-writer.ts` owns the intent, applies patches synchronously, serialises writes and drops superseded replies. Building a write from React's render-scoped `settings` loses that race and silently undoes the previous change.
- **Claude Code hints share the user's Max usage windows.** That is stated in Settings and in the README. It is the one thing a user can be genuinely surprised by; do not quietly drop it.
- **There is exactly one way to read the page, and it is guarded.** `capturePage` in `App.tsx` is the only caller of `client.capture`; the raw read is anonymous inside it, so an unguarded capture is not something a new call site can accidentally write. Every read is stamped with `sessionWriter.epoch` - the navigation epoch, bumped whenever the panel adopts a different problem - and discarded at _resolution_ if that epoch has passed. Resolution, not initiation: at initiation everything still looks consistent, and a late capture of the problem the user left otherwise classifies as an ordinary refresh and walks the panel back to it. The epoch counts problem changes rather than comparing slugs, so A → B → A is stale too. `ifStillCurrent` returns `{current:false}` rather than `null` because "navigated away" and "page unreadable" need opposite handling - the first abandons the turn, the second falls back to what is on screen.
- **Discarding stale reads is not enough on its own; the follower also settles.** Navigating A → B → C leaves two reads in flight, and if B's lands first the panel adopts B, which correctly invalidates C's read - and would strand the panel on B while the page shows C. So after every adoption the follower reads again, in the new epoch, until the page and the panel agree. It converges because a capture matching what was just adopted classifies as `refreshed`. The loop resolves ordering within one burst of tab events; it does not poll, so a later navigation is caught by its own event.
- **The epoch settles reads across problems; `capturedAt` settles them within one.** Two reads of the problem already on screen are routinely in flight - the panel captures on focus, on tab events and again at the start of every turn - and the epoch cannot separate them, because it never changed. So `classifyCapture` demands a _strictly newer_ `capturedAt` before calling a same-problem capture a refresh, and ties keep the incumbent. Without that the loser overwrites the winner and the panel walks back to a staler buffer, language and run result - and `snapshotForTurn` then runs the turn against it. The comparison is against `showingRef`, never a render closure, for the same reason `session-writer.ts` and `settings-writer.ts` hold their state outside React: whatever arbitrates a race cannot itself be render-scoped. `showSnapshot` is the only writer of `snapshot`; keep it that way or the ref goes stale and the guard silently stops guarding.
- **The panel follows the page, and a problem switch resets the ladder.** LeetCode is a single-page app, so the user can navigate with the panel open. A capture whose slug differs from the one on screen is not a stale read to discard - it is a navigation (`src/panel/problem-switch.ts`). Carrying panel state across it would run the next turn against a statement the user has left, persist the reply into the wrong session, and carry the _rung_ over, which hands out rung-4 pseudocode on a problem where nothing was earned. So the old session is written under its own slug first, then `sessionWriter.setActive` makes writes for any other slug impossible, then everything resets to rung 0.
- **A clear is refused by identity, not by time.** Every store here is a read-modify-write over one `chrome.storage.local` key, so all of them queue (`src/background/write-queue.ts`) - two overlapping upserts otherwise read the same "before" and the second `set` drops the first. Ordering is only half of it: `onDone` in `App.tsx` fires from a closure built when the turn _started_, so a turn finishing after "clear all saved data" is issued after the clear, arrives after it, and still describes the session the user deleted. A wall-clock cutoff cannot express that - the panel stamps the replacement session's `startedAt` before the worker hears about the clear, so any "older than the clear" rule refuses the replacement too. So the clear names the identity the panel is starting instead (`activeFrom`) and `src/background/clear-boundary.ts` refuses anything that began strictly earlier, at write time. Settings are deliberately outside all of this: a whole-value write on its own key, already serialised by `settings-writer.ts`, and a preference that survives the clear.
- **A saved session exists to protect the usage window, so it restores the rung too.** `src/background/transcript-store.ts` keys transcripts by problem slug and carries `startedAt` across resumes, because that is the session log's upsert key - drop it and one problem-sitting becomes several attempts that each report a shallower deepest rung than the truth. Every write clamps four separate bounds and prunes to `MAX_SESSIONS`; a transcript store with no ceiling would quietly become the largest thing the extension owns.
- **Topic tags are model context and only model context.** They name the technique, they sit behind a collapsed toggle the user has usually not opened, and they are gated three ways: the panel may not display them at any rung (`tests/prompt-gating.test.ts` reads `src/panel/`'s own source and fails if `topicTags` is so much as named there - which is why the paste form's `ProblemContext` constructor lives in `src/shared/pasted-problem.ts`), the system prompt states the boundary, and below rung 2 the spoiler guard strips tag names out of the stream. The guard covers tags but deliberately not `TECHNIQUE_NAMES`: those words have innocent uses, and the asymmetry is that a tag is something the user has _not seen_.
- **The tag guard withholds a concept, not a string.** `src/prompt/tag-forms.ts` owns the surface forms: case, separators between words (space/hyphen/underscore/none, bounded to 3 chars so a tag cannot span a paragraph break), number in both directions, possessives, and verbal/adverbial inflection of a _stem_. Stemming happens on the tag, once - the streamed text arrives a fragment at a time and cannot be stemmed - so the inverse shows up as the allowed suffix set. Synonyms, abbreviations ("DFS") and paraphrase are deliberately out: matching them mechanically means matching ordinary English. `TECHNIQUE_NAMES` in `rungs.ts` covers those in the prompt instead.
- **The breadth is only affordable because of `visibleText`.** LeetCode tags a problem `Array`, `String`, `Tree`, `Sorting` as readily as `Hash Table`, so withholding every tag turns a rung-1 reply into "you scan the [withheld] twice" - useless, and a signal in itself. `withheldTags` therefore drops any tag the user can already read in the title/statement/examples/constraints. That is not a hole in the rule, it _is_ the rule: the guard exists because the user has not seen the tags. Omitting `visibleText` withholds everything, which is the safe default for callers without the problem text.
- **The tag matcher and the stream-boundary check must agree on what a separator is.** Both run through `canonical()` in `spoiler-guard.ts`, which collapses every run of whitespace or hyphens to one space. They diverged once, and the result was a silent leak rather than a visible bug: the matcher was separator-flexible but the held-back-tail check compared raw characters, so `"…a Hash\n"` + `"Table…"` found no tag starting with `"hash\n"`, released "Hash" to the panel, and then never saw the two halves together. They can disagree in the other direction too: the hold-back once compared _stems_ to raw text, so "Slidi" on its way to "Sliding Window" (stem `slid`) matched nothing and the fragment went out. The hold is now its own regex (`tagPrefixPattern`), not a prefix comparison. Anything touching either side needs `tests/tag-morphology.test.ts`, which cuts every form of every real LeetCode tag at every offset.
- **The page picks the type as well as the value.** The MAIN-world bridge runs in page context, so `PageBridgeResponse` is a hostile-shaped object, not a trusted peer's. Two rules follow. `normaliseLanguageId` takes `unknown` and is **total** - an allowlist that throws on hostile input is not an allowlist. And the bridge listener in `content-script.ts` wraps its whole body in `try/catch`, because past `clearTimeout` there is no safety net left: a throw there does not crash, it _hangs_ - the promise never settles, `sendResponse` is never called, and `PortClient` has no timeout on one-shot requests, so the panel silently stops answering clicks. `tests/content-script.test.ts` drives the real listener with non-string languages and fails with `'HUNG'` if either rule is removed.
- **Everything gleaned goes through the same fence as everything else scraped.** The topic tags and every run-result field are wrapped by `pageDataFence` exactly like the statement is, one `field=` per value; the prose around them - the tag warning, `Source: Run…` - is Socrates' own account and stays outside. The run result is the case that makes a fixed delimiter unusable: it is the judge echoing the user's own program back, so a value containing ``` is the _ordinary_ case rather than an attack. A new scraped field goes inside a fence and gets a case in `tests/prompt-injection.test.ts`; unfencing one turns seven of them red.
- **Two `languageLabel`s, composed, not chosen.** `shared/languages.ts` maps an allowlisted id to LeetCode's own display name; `prompt/system-prompt.ts` reduces whatever comes out to a short punctuation-free label. The allowlist passes an _unrecognised_ id through rather than guessing, and the reducer is what stands behind that passthrough, so both run - `languageLabel(languageName(id))` - anywhere the language is named outside a fence.
- **Everything past the description is optional by construction.** The language toolbar, the tags, the hints disclosure and the run-result panel each parse to `null`/`[]` when absent and none of them can fail a scrape. Only the description is load-bearing. Editorial and hints are read as booleans and never as content - they are LeetCode's own ladder, written to a different discipline than this one.
- **The panel mirrors LeetCode's editor language, and a manual pick stops it.** `src/shared/languages.ts` is the single list; its ids are LeetCode's own slugs, which is also what Monaco reports (`golang`, `python3`, `csharp`), so no translation table is needed. The toolbar label is read _as well_ and wins, because it survives the Monaco bridge timing out. The effective language rides on `AskRequest.language` rather than being written over `snapshot.editor.language`: what the page says and what the user asked for are different facts and the panel shows both. Changing the editor language fires no tab event, so the follower also runs on the panel's `focus` - and it adopts `refreshed` captures rather than dropping them, or the picker would go on claiming the old language while the turn answered in the new one.
- The extension is read-only on leetcode.com: no typing, clicking, or submitting.
- All LeetCode selectors live in `src/content/scrape/selectors.ts` as fallback chains. DOM drift should be a one-file change, and when it is not, the paste fallback keeps the tool usable. `RESULT_LABELS` lives there too: the console panel labels its blocks with translated plain text and no markup, so the English wording is a drift surface exactly like a class name.
- **Thinking text must never leave the native host.** Extended thinking drafts the _answer_ - in a measured rung-1 run the thinking block held a complete, word-counted draft of the reply. `parseClaudeLine` therefore maps `thinking_delta` to an empty `{ kind: 'thinking' }` heartbeat and drops its text. Anything that surfaces thinking content routes the whole reply around the ladder. `tests/streaming-ux.test.ts` asserts the parser cannot carry it.
- **Liveness is a heartbeat, not an edge.** `claude-thinking` repeats (throttled by `THINKING_PULSE_MS`) for as long as frames arrive without text, because `src/panel/turn-progress.ts` decides whether to say "still working - long think" purely from the gap since the last event. De-duplicating the pulses anywhere on the path freezes the stall detector, which is why `claude-code.ts` forwards every one.
- **Dark is the primary scheme** in `src/panel/styles.css`, light is the `prefers-color-scheme: light` override. Every colour is a token declared in one of those two blocks; a literal outside them will be wrong in one scheme. Check both after any UI change. The tokens follow Catppuccin (Mocha for dark, Latte for light, https://catppuccin.com/palette) with a consistent semantic mapping - keep new tokens on-palette.
- **Rung colour is a graphic, never body text.** Each rung owns a hue (`--rung-0` … `--rung-5`, cool to warm) selected only by a `data-rung` attribute. Latte's warm accents sit near 2.4:1 against Base, so rung colour is confined to bars, borders, dots and washes; prose and button labels stay `--text` / `--rung-ink`, and a filled control uses the hue itself in Mocha but a 16% wash of it in Latte. Adding a rung-coloured element means checking it in both schemes.
- **Fonts are bundled locally** under `public/fonts/` (JetBrains Mono, OFL-licensed) and loaded via `@font-face` in `styles.css`. The extension CSP forbids remote font loading, so there is no `@import` from a font host; adding a typeface means vendoring its woff2 files the same way.
